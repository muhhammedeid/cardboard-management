# Backup and Recovery Readiness

**Package:** P05-W01 — MVP Operational Readiness & End-to-End Validation  
**Scope:** minimum non-destructive local/pilot backup procedure

Do not test a restore against the active site. Use a separate disposable bench/site and an approved maintenance window for recovery rehearsal.

## 1. What must be backed up

1. **Site database** for `cardboard.localhost`.
2. **Site files**:
   - `sites/cardboard.localhost/public/files`
   - `sites/cardboard.localhost/private/files`
   - `sites/cardboard.localhost/site_config.json` stored securely because it contains site secrets/configuration.
3. **Custom app/repository**:
   - the `apps/cardboard_management` Git repository and its commit/branch;
   - any uncommitted operational changes that are intentionally part of the pilot;
   - the installed app version and database migration state.
4. **Operational configuration record** from `MVP_INITIAL_SETUP.md` (values only; never passwords/tokens).

## 2. Database backup

Run from the bench root in WSL, with the site healthy:

```bash
cd ~/frappe/cardboard-bench
bench --site cardboard.localhost backup --with-files
```

Record the generated backup paths and copy them to storage outside the bench directory. Verify that the database backup file is non-empty and readable by the approved backup operator. Do not paste secrets into tickets or chat.

If a database-only backup is required:

```bash
bench --site cardboard.localhost backup
```

Use the exact backup file generated by Bench; do not manually copy live database files.

## 3. Site-file backup

`backup --with-files` is the preferred supported command. If an additional file copy is required, stop writes during the copy and preserve both public and private files:

```bash
tar -czf /safe/location/cardboard-localhost-files.tgz \
  sites/cardboard.localhost/public/files \
  sites/cardboard.localhost/private/files
```

Protect `site_config.json` separately with restricted access. Never publish it in the repository or attach it to a support ticket.

## 4. Custom repository backup

From the app repository:

```bash
cd ~/frappe/cardboard-bench/apps/cardboard_management
git status --short
git rev-parse HEAD
git bundle create /safe/location/cardboard_management.bundle --all
```

For an uncommitted pilot workspace, preserve a patch as a separate controlled artifact after review:

```bash
git diff --binary > /safe/location/cardboard_management-working-tree.patch
git diff --stat > /safe/location/cardboard_management-working-tree.stat
```

Do not use destructive Git commands (`reset --hard`, checkout-discard, clean) as a backup or recovery step.

## 6. Recovery outline on a disposable copy

1. Provision a separate bench/site; never overwrite the active site.
2. Install the matching Frappe, ERPNext, and Cardboard Management revisions.
3. Restore the database using the supported Bench restore command and the approved backup file.
4. Restore public/private files and the site configuration with appropriate permissions.
5. Run migrations only after confirming version compatibility.
6. Read back Cardboard Dashboard Settings, app versions, key DocTypes, and permissions.
7. Run `frappe.ping`, the focused runtime suites, and the UAT read-only/report checks.
8. Compare record counts, settings, stock, supplier outstanding, and native links against the backup verification record.
9. Record the recovery result; do not call recovery complete based only on a successful restore command.

The exact `bench restore` invocation depends on the backup filename and database credentials; obtain the approved operator command from the environment owner rather than guessing credentials.

## 7. Current readiness note

No destructive restore test was performed against `cardboard.localhost`. Backup/recovery is therefore documented and ready for a controlled rehearsal, but not manually signed off until an owner verifies a disposable-copy restore.
